## 先に結果

- LM Studioで `seed = 42` とし、`temperature` を0・0.3・1.2に変えて、FizzBuzzと俳句を各条件3回生成した。
- `temperature = 0` では、各タスクで3回とも同じ結果になった。最大スコアのトークンを選ぶ設定で、出力の再現性を確認できた。
- FizzBuzzでは、0で仕様に合う関数が得られた一方、0.3と1.2では不具合を含む回答もあった。少数の試行なので、不具合の発生率までは判断できない。
- 俳句では、季節に合わない季語の説明や、指定した句数との不一致が見られた。プロンプト自体にも「5-7-5」と「破調を積極的に使用」という曖昧さがあった。
- 表示された推論テキストの言語は条件や試行によって変わったが、言語が出力品質の原因であるかは、この実験では切り分けられていない。

## きっかけ

[前回の記事]({{< relref "posts/2026/02/14/index.md" >}})でローカルLLMのクラッシュと推論崩壊に苦しめられた。Context Lengthの設定を見直すとともに、「そもそもパラメータをどう設定すれば望ましい生成結果が得られるのか」という疑問が湧いた。

ここでは、`seed`を固定して`temperature`を変え、生成結果を比較した。`seed`を固定しない場合も予備的に試したが、seed値を系統的に変える比較実験は行っていない。

### temperatureとseedの役割

`temperature`は、次のトークンを選ぶ際の確率分布を調整する値である。正の値では、一般に低くすると高スコアの候補に集中し、高くすると低スコアの候補も選ばれやすくなる。

**`temperature = 0`では、各ステップで最大スコアのトークンを選ぶ。** この方法をgreedy decodingと呼ぶ。モデル・入力・計算条件をそろえると、同じ入力から同じ続きを返す関数のように動く。今回も、この設定ではFizzBuzzと俳句のそれぞれで3回とも同じ結果が得られた。

`seed`は、確率に従ってトークンを選択する際に使う擬似乱数の初期値である。モデルが計算したスコアをもとに、どの候補を選ぶかに関わる。サンプリングを使う条件でseedを固定すると、乱数列をそろえて比較できる。通常のgreedy decodingでは、最大スコアの候補が直接選ばれる。

予備的な試行では、seedを固定せずに`temperature = 0`で実行した際にも出力の違いが見られた。その後、seedを42に固定して比較したところ、各タスクで同じ結果が得られた。ここでは、そのときに使った設定と観察結果を記録している。

### 比較条件と結果の一覧

seedを42に固定し、各タスク・各temperatureで3回ずつ生成した。temperatureが0のときは同一の回答になり、0.3と1.2では同じ設定でも回答に違いが見られた。

| FizzBuzz |         0.3 |      3 | 1・3回目は変数iを文字列として出力、2回目は0と同じ実装            |
| FizzBuzz |         1.2 |      3 | 実装の表現が変化。不具合を含む回答もあり、全件の合否内訳は未集計 |
| 俳句     |           0 |      3 | 同一の回答。表示された推論テキストは中国語                       |
| 俳句     |         0.3 |      3 | 回答が変化。3回目は反復が続き、最後まで生成できず                |

## 実験①：プログラムコードを生成する（FizzBuzz）

### プロンプト

```text
あなたは以下のMain.javaを読んでいます。
適切な形でfizzbuzz関数を実装してください。
不必要に思考せず、簡潔に答えてください。
```

```java
class FizzBuzz {
    public static void main(String[] args) {
        for (int i = 0; i < 50; i++) {
            fizzbuzz(i);
        }
    }

    private void fizzbuzz(int i) {
        // TODO: Implement here
        // Spec:
        // - This function print:
        //   "i: fizz" if i is multiple of 3
        //   "i: buzz" if i is multiple of 5
        //   "i: fizzbuzz" if i is multiple of both 3 and 5
        //   "i: -" if others
        // - Each line should be ended with break line.
    }
}
```

### temperature = 0の場合(3回とも完全に同一のコードが生成される)

3回とも完全に同一のコードが生成された。表示された推論テキストは英語だった。下記の関数は目視では仕様に合っている。

```java
private static void fizzbuzz(int i) {
    if (i % 15 == 0) {
        System.out.println(i + ": fizzbuzz");
    } else if (i % 3 == 0) {
        System.out.println(i + ": fizz");
    } else if (i % 5 == 0) {
        System.out.println(i + ": buzz");
    } else {
        System.out.println(i + ": -");
    }
}
```

### temperature = 0.3の場合 （やや多様）

バグが混入した。`i`を変数ではなく文字列リテラルとして出力してしまっている（1回目・3回目）。

```java
// 1回目・3回目（バグあり）
private void fizzbuzz(int i) {
    if (i % 15 == 0) {
        System.out.println("i: fizzbuzz");  // ← iではなく"i"になっている
    } else if (i % 3 == 0) {
        System.out.println("i: fizz");
    } ...
}
```

2回目はバグがなく、`temperature = 0`のときと同じ実装が得られた。条件分岐の方針は3回とも同じだったが、出力文字列に違いが出た。この3回だけで、temperatureを上げると一般に精度が落ちるとは結論できないが、揺れが出ていることは観察できる。

### temperature = 1.2 （多様）

FizzBuzzの条件判定が`if i % 15 == 0`から`if i % 3 == 0 && i % 5 == 0`に変化するなど、より多様な実装が出た。引き続きバグを含む回答も混じった。

3回目には **推論過程が初めて日本語になった**（1・2回目は英語）。また、`fizzbuzz()` メソッドのみを出力し、`main()`を出力しないケースもあった。

```java
// 3回目（temperature=1.2、推論が日本語になった回）
private static void fizzbuzz(int i) {
    if (i % 15 == 0) {
        System.out.println(i + ": fizzbuzz");
    } else if (i % 3 == 0) {
        System.out.println(i + ": fizz");
    } else if (i % 5 == 0) {
        System.out.println(i + ": buzz");
    } else {
        System.out.println(i + ": -");
    }
}
```

なお、すべての試行を通じて、「`if i % 3 == 0`を先に評価してしまうミス」は一度も発生しなかった。

### コード生成の観察まとめ

今回の3回ずつの比較では、temperatureが0のときに同一の関数が得られ、0.3と1.2では不具合を含む回答もあった。temperatureと不具合の発生傾向について、より確かな結論を得るには、試行数を増やしたり、入力するプロンプトや実装課題を変えたりして検証するとよいと考えられる。生成コードをコンパイルし、仕様に沿ったテストで評価すれば、条件ごとの違いも比較しやすくなる。

## 実験②：俳句を生成する

以下のプロンプトを使った。「5-7-5」を指定しながら破調も積極的に求めており、形式の評価基準が曖昧だった。そのため、音数が5-7-5でないことだけを失敗とは判定しない。季節との整合性、指定した3句への対応、日本語の表現を分けて観察する。生成文に含まれる季語や音数の説明は、モデルの回答をそのまま引用したもので、正しい解説とは限らない。

```text
2月の季語を使いながら俳句を生成してください。
- 形式は5-7-5
- 冬の終わりの静寂さとの別れを彷彿させる俳句
- 破調（5-7-5の崩れ）も積極的に使用  // ← わざと揺れさせるように
- 対比する句を3句作成（例：朝・昼・夜）  // ← わざと揺れさせるように
```

### temperature = 0の場合 （今回の3回は同一出力）

推論が **中国語** で行われた。3回とも完全に同一の結果で、推論言語も変わらなかった。

（推論の一部）

```text
嗯，用户想要用2月的季语创作俳句，主题是冬末的静寂感和离别氛围，
还特别要求使用破调和对毎句。这个需求挺有意思的，看来用户对俳句有一定了解...
```

出力された俳句は以下のとおり（全3回共通）。

> **句1: 朝の雪が舞い散る窓**
> 静かに静かに静かだ
> 冬の終わりを告げる
> この季節の美しさは憂いを帯びて
>
> **句2: 午後の枯枝が揺れる風**
> 冷たく冷たく冷たい
> 待ち続ける季語たちの
> ささやく別れの言葉
>
> **句3: 夜の灯りが揺れる窓**
> 孤独に孤独に孤独だ
> 季節は去りゆくが
> 心はまだ冬の静寂に囚われて

想定していた短い句とは異なり、説明的な複数行の詩になった。繰り返しも目立つ。ただし、破調を許容した指示の影響と、推論テキストの言語が影響した可能性も考えられる。

### temperature = 0.3の場合 （やや多様）

引き続き推論は中国語で行われた。ただし `temperature=0` と同一の推論過程ではなく、出力にも多様性が出た。

1回目はプロンプトに答えていない句が出た。回答の一部には、中国語の簡体字を含む表記（`阴り`）があった。

> **句例1:**
>
> 窓の外の雪が融け出す
>
> - **季語:** 雪が融け出す (雪解けの始まり)
> - **イメージ:** 冬の終わり、雪が消え始める静寂と、その過程での期待や寂しさを表現。
>
> **句例2:**
>
> さくらんぼの花が咲き出す
>
> - **季語:** さくらんぼの花 (2月の梅の花、暁花)
> - **イメージ:** 別れを彷彿させる、美しいが儚い花の開く様子。破調（5-7-5）ではありますが、季語と題意を満たしています。
>
> **句例3:**
>
> 日は阴り少なくなった
>
> - **季語:** 日は阴り少なくなった (日陰が減った、日照時間が長くなった)
> - **イメージ:** 冬の厳しさが和らぎ、春に向かう静かな変化。別れの訪れを暗示。

2回目は1回目と大きく変わり、異なる季語・構成になった（今回の例では、コードの条件分岐よりも文章の構成の違いが目立った）。

> 1. **季語：立春**
>    - **句：** 立春の木枯らぎ / さよなら雪 / 窓の外で待ち
>    - **説明：** 「立春」が季語、「木枯らぎ」（枯れ木）が2月の風景を表す。破調の6-7-5で始まり、冬の終わりの静寂と去りゆく雪、窓の外で待ち続ける情景を描く。
> 2. **季語：梅雨**
>    - **句：** 梅雨の朝露 / かすかに春の匂い / うっかり吸い込む
>    - **説明：** 「梅雨」が季語、「朝露」が2月の季語風景。破調の5-7-5で、ほのかな春の匂いを帯びた湿った空気を、つい意識せずに吸い込む無邪気さを表現。
> 3. **季語：雫**
>    - **句：** 雫の花蕾 / 未だ届けられぬ手紙 / 春待ちの季語
>    - **説明：** 「雫」（しぶき、滴）が季語、「花蕾」（芽）が春の訪れを象徴。破調の5-5-5で、まだ届いていない別れの手紙と、待ち続ける季語の重ね合わせを表現。

3回目は **反復が続き、俳句を最後まで生成できなかった**。このときは`repeat-penalty = 1.0`で、繰り返しへのペナルティをかけない設定だった。次に試す際は、この値を上げて比較すると、反復の抑制にどの程度効果があるかを確認できると考えられる。

### temperature = 1.2の場合 （多様）

1回目は、短い表現になり、説明的な言葉が控えられている点に注目した。中国語で推論されていた。

> - 朝霜降る 春待ちかな
> - 雪降り 山の間は 静かに
> - 夜の季語に 山は青し

2回目は **日本語で推論** した。ただし、指定した3句に対して6句を出力し、「梅雨明け」など2月の指定に合わない語も含まれていた。日本語の推論テキストが表示された回でも、指示への不一致は残った。

（2回目の推論）

```text
まず、ユーザーのクエリを理解します。ユーザーは2月の季語を使って俳句を作成してほしいと要請しています。
```

1. 二月寒風、枯れ木そよぐ静かに、別れの訪れ

3. 古池の水面結晶、冬が終りを告げる、孤独な夜
4. 6-7-5の句：風雪舞う空庭、往く者もなしの別れ、季節の幕下り

3回目は、やや説明的な言葉が目立った。こちらも、表示された推論テキストは中国語だった。

> **1. 朝：** 正月に雪かすがり、君はもう去りぬ 
> **2. 昼：** 窓辺、霜枯らむ、そよ風立ち込める 
> **3. 夜：** 長閑、月光の下、さよならの言葉響く

### 俳句生成のまとめ

temperatureが0では、今回期待していた俳句は得られなかった。0.3は表現のバランスが比較的よいと感じたが、季語の誤った説明や生成が完了しない試行もあり、最適値と判断できる結果ではない。1.2では日本語の推論テキストが表示された回もあったが、句数や季節の指定は守られなかった。

プロンプトで複数の要求を同時に与えたことが影響した可能性もある。そのため、まず「破調なしで5-7-5」と「破調を許容する創作」を別のプロンプトに分けるとよいと考えられる。音数、季語、句数、表現の好みを別々に評価すれば、設定の違いを比較しやすくなる。実行パラメータを調整するには、小さなタスクでの出力結果の比較検討が必要と思われる。

## 表示された推論言語と品質の関係

今回、同じ日本語の依頼でも、表示された推論テキストには英語・中国語・日本語が現れた。これは興味深い観察だが、**推論テキストの言語が品質の原因だとは言えない**。

俳句では、中国語の推論テキストが表示された回答に問題があった一方、日本語が表示された回答にも季節や句数の不一致があった。言語以外の生成内容も同時に変わっているため、言語だけの効果は比較できていない。

また、この出力からモデルの訓練データの言語比率や、日本語俳句の知識量を推定できない。「中国語で考えたから俳句の形式を守れなかった」という説明は仮説にとどまる。

## さらに検証する場合の設定と確認方法

コード生成では、モデルの公式推奨設定を比較の基準にし、必要に応じて低いtemperatureや、場合によってはtemperature = 0も試す。サンプリングを使う場合はseedも記録し、モデルのファイル・量子化方式・推論エンジン・プロンプト・会話履歴・その他の設定をそろえる。そのうえで、生成コードをコンパイルし、0・3・5・15のような分岐を通る値と、通常の値で出力を確認する。temperatureで出力の傾向を調整し、テストで正しさを確認する。

俳句のような創作では、先に守るべき条件を明確にし、temperatureを変えた回答を複数回比較する。今回、比較的バランスがよいと感じた0.3を出発点に、モデルやタスクに合わせて値を調整すると、適した設定を探りやすくなると考えられる。

反復が続く場合は、生成トークン数に上限を設けたうえで、繰り返しペナルティの値を変えて比較するとよいと考えられる。繰り返しペナルティは1.0で補正なしとなる。値を上げれば既出トークンへのペナルティが強くなるため、反復が続くときの調整候補になる。

## まとめ

本比較では、seedを42に固定してtemperatureを0にすると、FizzBuzzと俳句のそれぞれで、各3回の出力が一致したことを確認した。一方、temperatureを上げた条件では、実装や表現に違いが見られた。俳句の指示への適合は、temperatureの変更だけでは改善しなかった。

各条件3回の比較で、出力の再現性と指示への適合は別々に見る必要があると感じた。同じ回答が返っても、それが期待した回答とは限らない。モデルやタスクを変えて調整する際にも、この2つを分けて評価することが有効だと考えられる。

## 追加検証の観点

より確かな結論を得るための検証として、次の方法が考えられる。

- サンプリングを使う条件でseedの値を変え、出力の違いを比較する。
- 俳句のプロンプトについて、小さなタスクに分解し、音数・季語・句数を別々に評価する。
- 日本語の俳句生成に適したモデルでも同じ条件を試し、モデル間の違いを比較する。
