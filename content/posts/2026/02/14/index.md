## TL; DR

- ローカルLLM（LM Studio） + AiderでSpec Driven Development（SDD）を試したが、実用には至らなかった
- 14Bクラスのモデルでは推論性能が不足し、以下のような問題が頻発した。
  - 仕様外のファイル生成
  - 過剰修正
  - 英語/日本語のコード再生成ループ
- 一方で、より大きなモデルは メモリ制約（MacBook M3 / 24GB）で動かせない
- Deepseek系モデルでは、エンジンの設計上のトレードオフに直面した
  - MLX：OOMで即クラッシュ
  - llama.cpp：OOM後も動き続けるが推論崩壊が発生
- 推論性能が低いほど、開発者側に高度な仕様記述スキルが要求される
  - ローカルLLMでSDDをするには、SDDが不要なほどの知識と熟練が必要
- Context Lengthは後から調整するものではなく、KV Cacheとメモリ量を踏まえた事前の設計判断が必須
- ローカルLLMは「クラウドLLMの安価な代替」ではなく、オンプレAI基盤としての設計・運用能力を要求される計算基盤
- 結論としては、現時点の個人環境では、ローカルLLMで実用的なSDDを行うのは現実的ではない。

## 背景

昨今、生成AI(クラウドLLM)に渡したくない情報をローカルLLMで処理したいという要望がある。一方で、Claude CodeのようなクラウドLLMと比較すると、(ローカルLLMを動かす環境にもよるが)処理性能やパラメータの設計に難点がある。

また、個人的に _Spec Driven Development_ （SDD）を試してみたいと思っていた。クラウドLLMを使えばそのまま実践できるが、実験を何度も繰り返すにはコストが気になる。

そこで今回は、一般的に入手し易いMacBook Air M3を使用してローカルLLMでSDDを実践することを通じて、ローカルLLMの難点を体感すると同時に、ローカルLLMでSDDがどこまで実践できるのかを実験してみることにした。具体的には「LM StudioのOpenAI互換APIにAiderのバックエンドを向け、ローカルLLMでSDDを実行する」ということである。

ちなみにここでいうSDDとは、AIに対して厳密な仕様書（プロンプト）を与えることで実装を自律的に行わせる開発手法を指している。

予め申し上げるが、この記事はあくまでMacBook Air M3(24GB RAM)の環境でできたことをまとめたものであって、ローカルLLM全般や、他の環境での実用性を評価したものではない。

### 環境

主に使用した環境を以下に示す。

- マシン: MacBook Air M3
- メモリ: 24GB
- モデル: `qwen/qwen2.5-coder-14b`
- LM Studio: 0.4.2+2
- Aider: 0.82.3

## 実装対象

Kotlin製のAndroidアプリ「Habit Tracker」を実装することにした。SSoT(Single Source of Truth)な情報源として仕様書を作成し、以下のような内容を記述した。可能な限りトークン消費を減らすため、実際の仕様書には英語で記述した。

- 習慣を作成、更新、削除できる。
- 習慣の継続状況を記録する。回数ではなく、その日に実行したかどうかを記録する。
- 習慣を削除したあとも、過去の継続状況を確認できる。
- 最初のMVPでは、習慣の作成、更新、削除だけを実装する。
- MVP範囲外の機能や、指示していない改善を追加しない。

また上記の他に、パッケージ名、Kotlinを使用すること、Minimum SDK、ソースコードとテストの配置先(ディレクトリツリー)を指定した。

## 試行の記録(`qwen/qwen2.5-coder-14b`)

仕様書を渡して実装を依頼すると、主に3つの問題が発生した。

1. 指定したディレクトリ以外にファイルが生成される。
2. 指示にない画面の文言修正が続く。
3. 同じコードを繰り返し生成する。

一つずつ説明する。

### 指定したディレクトリ以外にファイルが生成される。

仕様書には、ソースコードの配置先を記載していたが、実際には意図しないディレクトリにファイルが生成された。よって、人間がレビューする際に、どのディレクトリにファイルが生成されたのかを確認する必要があり、LLM単独では実行可能なバイナリ(APKパッケージ)を作成することができなかった。

### 指示にない画面の文言修正が続く。

機能の追加やバグを改修するように指示をしたところ、それとは無関係である画面の文言修正を繰り返した。そもそも生成に時間がかかることに加え、人間のレビューの負荷が高くなるほか、AIの作業のモニタリングに非常に苦労した。

### 同じコードを繰り返し生成する。

仕様書は英語で記述していたことから、推論、コード生成も英語で行われた。それはよいのだが、問題は英語による処理が終わったあとに、日本語でも推論、コード生成を行う挙動が見られた。つまり、画面上に色々と出力はされるものの、実装が先に進まない状態であった。

これらの結果から、必ずしも「14Bクラスのモデルには実装能力が足りない」とまでは言えない。モデルの能力に加え、ローカルLLMのパラメータ設定やAiderとの組合せ、渡した情報量、仕様の曖昧さなど、様々な要因が絡んでいると思われる。今回は、そこまでの切り分けを行わず、安易にモデルの変更を試した。

## DeepSeekへの変更と、長い出力での問題

別のモデルでも試してみるべく `DeepSeek R1 0528 Qwen 3 8B`に切り替えた。ちなみにこの判断は、このモデルのサイズであれば、24GBのメモリに完全オフロードできるからである。

また、今回は、仕様書に沿った実装がうまく進むか進まない理由がモデルにあることを特定することを目的とはしなかった。他にどのような課題が出るかを知りたいという興味がでてきたからである。そのため、今回は `qwen2.5-coder-14b` のときと同じパラメータを使うということはしていない。

ここで生じた問題点は以下の2点であった。

1. MLXでは生成途中にエラーが発生した。
2. llama.cppエンジンに切り替えたところ、生成が続いたが、推論内容が乱れた。

ちなみに、MLXやllama.cppエンジンというのは、LM Studioでモデルを動作させるときに使用するためのバックエンドエンジンのことである。

一つずつ説明する。

### MLXでは生成途中にエラーが発生した。

MLXでは、メモリ確保に失敗すると例外が発生する。LM StudioのMLXバックエンドは、生成中の例外を捕捉すると、進行中のリクエストへエラーを通知し、生成処理を終了する

```python
litellm.APIConnectionError: APIConnectionError: OpenAIException - Error in iterating prediction stream: Exception:
Encountered fatal exception in the backend scheduler: Traceback (most recent call last):
  File ".../mlx_engine/model_kit/batched_model_kit.py", line 216, in _generate_with_exception_handling
    self._generate()
  File ".../mlx_engine/model_kit/batched_model_kit.py", line 338, in _generate
    responses = batch_generator.next()
                ^^^^^^^^^^^^^^^^^^^^^^
  File ".../mlx_lm/generate.py", line 1266, in next
    return self._next()
```

今回の場合、生成されたトークンが11,000を超えたあたりでクラッシュしている。

### llama.cppエンジンに切り替えたところ、生成が続いたが、推論内容が乱れた。

次にクラッシュを回避するため、DeepseekをMLXフォーマットからGGUFフォーマットに変更し、`llama.cpp`バックエンドに切り替えたところ、11,000トークンを超えても回答を生成するようにはなった。

> しかし、今度は **推論崩壊** が発生した。`llama-cli`はOOMが発生しても`ctx_pos` / `n_past`が進み続ける設計であり、初期化が保証されていないKV Cacheを文脈として使い続けるため、推論が崩壊しながら処理を続けてしまうのだ。
> 
> これは、両者の良し悪しではなく、設計思想によるトレードオフである。

この表現は正確ではない可能性がある。過去に、Out of Memoryを検出する処理に不具合があり、不正な状態で処理が続いた可能性がある。従って、設計上の違いというよりも、不具合に影響を受けていた可能性がある。

## 試してわかったこと

### 仕様書を渡した後にも、確認と軌道修正が必要だった

今回の仕様書には、MVPの範囲や禁止事項を記載した。それでも、ファイルの配置、画面文言、生成の繰り返しを人間が確認し、修正を促す必要があった。

一方で、仕様書自体にも改善の余地はある。例えば「習慣を作成・更新・削除する」という要件だけでは、画面構成、入力項目、保存方法、完了とみなす条件までは決まらない。記載していない部分をどう実装するか、モデルに判断を委ねていたことになる。

モデルの挙動と仕様の不足を分けて考えるためにも、実装してほしい内容と、確認する基準を具体化する必要があると感じた。仕様書の具体化にあたっては、Planモードを使用し、AIから見た仕様書の不明点をつめていく工程が必要になると思われる。

### 小さな単位で依頼する方法を試したい

今回のように実装が進まなくなった場合は、画面、ファイル、関数などの単位に依頼を分け、それぞれの結果を確認する方法が考えられる。

ただし、今回の試行では、タスクを分割した場合に、どの程度改善するかまでは検証していない。次に試すなら、まず小さな変更を依頼し、指定したファイルだけが変更されるか、必要な機能が動作するかを確認したい。

### メモリ容量だけでは実行条件を決められない

ローカルLLMを使う際は、モデルのパラメータ数だけでなく、量子化方式、コンテキスト長、生成する長さ、同時に動かすアプリケーションも考慮する必要がある。

今回のMacBookはメモリ24GBで、Android StudioやChromeも使う環境だった。ただし、試行時の使用量を記録していなかったことから、本当にメモリ不足であったのかを断定することはできない。(恐らく、メモリが不足していたんだろうとは思われるが)

コンテキスト長も、最初から大きく設定すればよいわけではない。必要な入力と出力が収まる設定から始め、メモリ使用量や生成結果を確認しながら調整する必要がある。

### ローカルLLMでは、推論環境の管理も作業になる

今回はアプリの実装よりも、ローカルLLM環境の設定、調整に時間を要した。ローカルLLMを選ぶ際は、手元で動かせる利点とともに、この作業を引き受けられるかも考える必要があると感じる。

業務利用であれば尚のことである。オンプレミスで生成AIを動作させる場合には、データの扱いに関する要件に加えて、必要な生成品質を維持するための検証・運用体制を考える必要がある。それに時間を使うことができない、あるいはそのための人材がいない場合には、クラウドLLMを第一に検討したほうがよいと考えられる。

### ローカルLLMを使うには、オンプレミスのインフラ設計で求められるような設計を開発者に要求する

今回最も印象に残ったのは、「ローカルLLMはクラウドLLMの手軽な代替ではない」という認識だ。ローカルLLMはマシンスペックさえあれば手軽に試せるという文脈で紹介されがちであるが、実際に使おうと思うとかなり難しい。しかし、クラウドで提供される生成AIであればインフラのことを意識しなくて済む。しかしローカルLLMでは、モデルの選定・量子化方式・推論エンジンの選択・Context Lengthとメモリの関係など、これらをオンプレミス環境のサーバ運用と同等の感覚で設計する必要がある。

仕事では「セキュリティを要求する顧客にはオンプレの生成AIを提供すべきではないか」という議論が時たま起こるが、決してそんな単純な判断軸ではないと体感した。

## まとめ

LM StudioとAiderを組み合わせ、ローカルLLMに仕様書からAndroidアプリを実装させようとした。しかし、今回の環境と依頼方法では、意図しない修正や生成の繰り返し、長い出力でのエラーに直面し、実用的に進められる状態には至らなかった。

この経験から、ローカルLLMを使用する際には、少なくとも以下の点を考慮しながら、実用化に向けたトライエラーが必要になると考える。

- モデルの配布元、量子化方式、コンテキスト長、生成パラメータ
- 入力と出力の長さ、実行時のメモリ使用量
- 依頼した作業と、その完了を判断する基準
- 発生したエラーと、条件を変えたときの結果

また、それらによって設計したローカルLLMを使用する際は、その特性によってタスクを実行可能な単位まで落とすなども検討する必要がある。
